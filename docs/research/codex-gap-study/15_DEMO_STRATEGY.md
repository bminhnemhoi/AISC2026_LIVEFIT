# Three-to-five-minute demo strategy

Research date: **2026-10-05**. Repository: `rebuild/livelift-next`. This is research and a proposed product strategy, not implementation or proof of market demand. The [V3 master roadmap](../../roadmap/LIVELIFT_V3_MASTER_ROADMAP.md) governs future work; these reports supply evidence.

## Demonstration claim

“This team can see a timed commerce commitment becoming infeasible, make a deliberate recovery, then change tomorrow's actual plan.” Do not claim first rundown, autonomous native execution or sales lift. This story is a proposed demonstration; the current fixture prototype does not yet implement all steps. Label rehearsal and any simulated history prominently.

## Four-minute story

| Demo time | Scene and visible behavior | Why it matters / proof |
|---|---|---|
| 0:00–0:35 | Load a SIMULATED 30m show: Opening 20:00–20:03; A 20:03–20:09 (6m); buffer until 20:12; Flash Sale announcement 20:12–20:15 fixed; B 20:15–20:23; optional Q&A to 20:26; closing fixed 20:26–20:30. | Real plan, durations, minima and two hard anchors. Native commerce control is outside this demo. |
| 0:35–1:15 | Advance virtual time to 20:07. Host reports A needs 6 more minutes: projected end 20:13. Three minutes of buffer absorb part of the 4m overrun; Flash Sale is still at risk by 1m. | Forecast changes; anchor remains 20:12. WHY identifies the deficit and uncertainty. |
| 1:15–1:55 | Operator chooses “close A by 20:12; move unfinished points to later Q&A.” Preview checks product minimum/coverage and later closing. Advance to 20:12 and confirm transition. | Human decision protects the promise. A actually takes 9m; no fabricated platform action. |
| 1:55–2:20 | Optional validated Host View shows current/next/countdown and one closing cue. Operator separately marks native Flash Sale “Reported at 20:12,” or leave unknown and show the honest label. | Shared operational state, not an auto-pin or platform-confirmation claim. If Host View unbuilt, omit it and show operator display. |
| 2:20–3:05 | Finish accelerated show. Review shows A +3m, consumed buffer, on-time cue report, coverage/follow-up and original vs actual intervals. Native TikTok analytics link remains separate. | Review is generated from this run's commands, not a canned fixture. |
| 3:05–3:45 | Select A 9m, Opening 2m (minimum allows it), buffer 1m. Show a diff: A runs 20:02–20:11; buffer to 20:12; both anchors unchanged. Create next show; open Prepare to verify changed allocations and cleared actual history. | Selected changes truly apply; coherent next-plan loop is the central payoff. |
| 3:45–4:00 | State limits: manual/simulated operation, no sales causality; compare with the team's current sheet/native/rundown method. | Honest, defensible workflow contribution. |

The 2m opening change is an explicit tradeoff, not an automatically “learned” fact. One show supports a manual selected adjustment; a recurring duration claim requires at least three comparable completed occurrences with spread/sample count. Simulated prior records must never appear as real learning.

## Alternate failure branch

Replay the same seed but let A end 20:13. The 20:12 anchor stays visible as missed by 1m. The operator can acknowledge, cancel or start late; the software must not claim a recovered deadline by moving history. This 20-second optional branch is stronger reliability proof than a fake-perfect happy path.

The more severe original 20:00/5m, A/7m, 20:12 giveaway example and 4m missed-anchor behavior are specified in [P0](13_P0_SPEC.md). Do not confuse it with this buffered demo scenario.

## Is the story compelling enough?

It is a concrete, API-independent demonstration but not sufficient novelty by itself: Shoflo/Ontime/Rundown Studio handle timing, and Opsique advertises a related commerce loop. The final minute—recorded actuals and a validated selected next-plan change—is the intended differentiation. If the audience values only the countdown, the strategy is too weak. Add paired baseline evidence when available, not more AI effects.

## Demo acceptance

The presenter must demonstrate actual forecast recalculation, immutable anchors, a logged recovery, honest external-action status, review of this run and a materially changed clone. The scenario must repeat deterministically and survive a page reload using the functional backend checkpoint. No manual database edits, hidden precomputed “learning,” fake REAL integration status or production room actions. A static prototype may show the concept only if named as such.
